DOKOS est une PME créée en 2017 par Charles-Henri Decultot. Spécialisée dans les solutions ERP libres pour les organisations françaises et européennes. Le projet s'inscrit dans le contexte de la certification de caisse, où les données fiscales doivent être vérifiées sans modification.

Problématique

Comment garantir l’intégrité des données ?

Les données proviennent d'un fichier ZIP contenant :

  • 📦 Base SQLite (les données)
  • 🔐 Signatures digitales (.sig)
  • 🔑 Clés publiques (PEM)
  • 📜 Licences JSON
Les fichiers ZIP contiennent tout ce qu'il faut pour vérifier l'intégrité. C'est une architecture en "defense in depth" - plusieurs couches de vérification plutôt qu'une seule.

🎯 Objectif du Projet

  • ✅ Vérifier l'intégrité → Les données n'ont pas été modifiées
  • ✅ Vérifier l'authenticité → Données proviennent du bon émetteur
  • ✅ Détecter les altérations → Modifications, suppressions, réordonnements
  • ✅ Interface claire → Résultats visuels pour contrôleur fiscal
L'objectif est de créer une interface web permettant à un contrôleur fiscal de vérifier rapidement l'intégrité des données sans avoir à comprendre la cryptographie.

🔐 Architecture de Sécurité

Defense-in-depth : 3 niveaux indépendants

🔗 Niveau 1 : Chaînage des Signatures

Concept : Chaque enregistrement référence la signature du précédent

Enreg. 1: sig_1 = H(data_1)
Enreg. 2: sig_2 = H(data_2 + sig_1)  ← Référence sig_1
Enreg. 3: sig_3 = H(data_3 + sig_2)  ← Référence sig_2
...

✅ Détecte : Suppression, insertion, réordering
❌ Ne détecte pas : Modification de contenu

C'est comme une chaîne de blocks. Si on supprime un bloc au milieu, la chaîne se casse. Si on modifie un bloc, le suivant n'aura plus la bonne référence. Mais ne détecte pas si on change la donnée elle-même.

📝 Niveau 2 : Vérification Cryptographique

Algorithme : Ed25519 (asymétrique, courbes elliptiques)

Étapes :
1️⃣ Reconstruire JSON canonique (clés triées)
2️⃣ Charger clé publique (PEM → WebCrypto)
3️⃣ Vérifier signature = crypto.subtle.verify()

✅ Détecte : Toute modification du contenu
✅ Garantit : Intégrité + Authenticité + Non-répudiation
✓ Sûr : Timing-constant (WebCrypto), résistant timing attacks

Ed25519 est l'état de l'art. Rapide, sûr, moderne. WebCrypto native au navigateur = zéro dépendance. JSON canonique = format déterministe, même si données réordonnées, signature restera valide.

🌐 Niveau 3 : Vérification API (SAS)

Étape finale : Appel à API externe (Service d'Authentification Sécurisée)

✅ Confirme que la signature est enregistrée dans le système officiel
✅ Prévient fraude (signature cryptographiquement valide mais non officielle)

⚠️ Mitigations :
• HTTPS obligatoire • Timeout 5s • Validation structure réponse
Même si quelqu'un créait une signature valide cryptographiquement avec sa propre clé, il ne pourrait pas la faire accepter car elle ne sera pas dans le système officiel.

🎯 Résumé : 3 Niveaux se Contrôlent

Couche Détecte Garantit
Chaînage Suppressions/Insertions/Réordering Continuité
Cryptographie Modification contenu Intégrité + Authenticité
API Signature non officielle Conformité registre

✓ Seul : insuffisant | ✓ Ensemble : très élevé niveau de sécurité

Chaque couche protège contre un type d'attaque différent. Aucune seule n'est suffisante, ensemble elles forment une armor quasi-impénable pour le contexte fiscal.

🔍 Veille de Sécurité

Vulnérabilités investigguées & mitigations

📚 Méthodologie

  • 1️⃣ Documentation officielle (MDN, W3C, RFC)
  • 2️⃣ Dépôts GitHub (issues, CVE, patterns)
  • 3️⃣ OWASP & Ressources sécurité (Cheat Sheets, Top 10)
  • 4️⃣ Forums & communautés (Stack Overflow, r/netsec)

Recherches en anglais : Documentation originale complète & à jour

Méthodologie systématique. Les sources anglaises sont plus à jour car c'est là que la recherche se publie d'abord. Les traductions françaises retardent souvent de 6-12 mois.

🔐 Vulnérabilités Identifiées

✅ Timing Attacks (Ed25519) : Mitigé (WebCrypto timing-constant)

✅ JSON Key Ordering : Mitigé (safe-stable-stringify + RFC 8785)

✅ Clés PEM invalides : Mitigé (validation try/catch robuste)

✅ Cache inefficace : Mitigé (Map UUID → Key, 85% perf gain)

✅ Chaînage cassé : Mitigé (vérification stricte sequence_id)

✅ API spoofée : Mitigé (HTTPS + timeout + validation)

✓ Aucune vulnérabilité critique trouvée

Veille exhaustive menée. 6 vulnérabilités potentielles identifiées et mitigées. Aucune critique en production. Application ready-to-deploy du point de vue sécurité.

⚠️ Recommandations Futures

1. Horodatage (Timestamps) :
Ajouter vérification d'expiration (ex: signatures > 10 ans invalides)
Effort: 2-3h | Impact: Moyen

2. Révocation de Clés (CRL) :
Maintenir liste clés compromise/révoquées
Effort: 4-5h | Impact: Élevé

3. Audit Logging :
Logger chaque vérification + exporter dans fichier signé
Effort: 3-4h | Impact: Moyen

Ces améliorations renforceraient la sécurité sur le long terme. CRL est critical si une clé est compromise. Horodatage pour éviter "signatures zombie" très anciennes. Audit logging pour détection d'anomalies.

🛠️ Détails d'Implémentation

Front-end et back-end

🎨 Front-end

  • HTML + CSS : Structure sémantique, grid layout, Bootstrap responsive
  • JavaScript natif : Manipulation DOM, gestion événements, async/await
  • Pagination : 500 lignes/page, navigation fluide
  • Cas particuliers gérés :
    • Tables enfants → bouton vérifier désactivé
    • Tables "étoile" (vues) → export seul, pas de vérification
    • Tables vides → message alerte clair
Front-end très propre et lean. Zéro framework pour minimiser bundle size et dépendances. Tout en vanilla JavaScript.

⚙️ Back-end (Logique Métier)

Composants principaux :

  • verifyByLine(): Vérification cryptographique par enregistrement
    • Import clé PEM → WebCrypto, JSON canonique, signature Ed25519
  • verifyChaining(): Vérification chaînage signatures
  • exportFactureCSV(): Export intelligente (3 tables en 1 CSV)
  • pairingSig(): Association signatures ↔ fichiers
  • licenseToKeyMapping(): Cache UUID → clé publique

Performance: 500 vérifications = 0.4s (avec cache) vs 2.3s (sans)

Back-end très optimisé. Cache UUID → Key améliore perf de 85%. Export factures complètes combine intelligemment 3 tables parent-enfant.

💾 Accès aux Données

  • sql.js : SQLite côté client (zéro serveur)
  • Récupération dynamique : Requêtes SQL générées selon sélection
  • Conversion CSV : Génération blob + téléchargement navigateur
  • Conversion JSON : Canonique + stable pour signatures
Avantage hors-ligne : Données ne quittent jamais le navigateur, pas de transmission sécurisée requise
Approche très sécurisée : données sensibles ne sont jamais envoyées à un serveur. Tout traitement local.
